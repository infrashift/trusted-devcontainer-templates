---
title: "ADR-009: Repo-Local Features"
description: Decision to build, test and publish the features the neovim-go template needs from this repository, under the same contract and release model as trusted-devcontainer-features.
---

**Status:** Accepted

## Context

The `neovim-go` template (tmux + Neovim/LazyVim + Go) needs four features that do not exist in [`trusted-devcontainer-features`](https://github.com/infrashift/trusted-devcontainer-features): `tmux`, `neovim`, `lazyvim` and `go-tools`. The template replaces a hand-built image (`devpod-neovim` in the hashistack collection). That image installed Neovim, Go and the Mason tools with `curl | tar` and no checksum, built its Go tools with `go install …@latest`, and synced LazyVim plugins against their branch heads with `|| true` hiding any failure.

Developing four features in the features repository and a template here would split one change across two repositories and two release cadences. Every iteration on the editor experience would then mean a feature release, a re-pin and a template rebuild.

## Decision

For their first version, the four features live in this repository under `features/`:

```
features/
├── src/<id>/            devcontainer-feature.json, install.sh, ansible-role-feature/
├── test/neovim-go/      a test template that stages features/src locally
├── test/shared/         test-lib.sh, contract-tests.sh
└── scripts/             contract, drift, bootstrap-pin, release scripts
```

They are published to `ghcr.io/infrashift/trusted-devcontainer-templates/features/<id>`, a namespace separate from the templates.

**Same contract.** Every role follows ADR-012 of the features repository: a thin `install.sh`, option defaults only in `devcontainer-feature.json`, a runner-contract assert, a parameter bracket that validates shape, per-arch pinned checksums on every download, verification of the exact requested version, and `changed=0` on a second run. `features/scripts/check-role-contract.sh` is a port of that repository's check. Moving a feature there later means copying the directory.

**Same release model.** `release-features.yml` stages to a private namespace (Build-Actor), reviews the staged digests and signs a verdict (Review-Actor), then signs and promotes exactly those digests (Release-Actor). The scripts are ports of the features repository's.

**Two differences, both forced by living outside that repository:**

- `dependsOn` names `bootstrap` by an absolute, digest-pinned reference, not `./bootstrap`. It must equal the bootstrap every template here pins; `check-bootstrap-pin.sh` enforces that on the pull request, and review re-checks the staged bytes.
- Releases run on **push to `main`**, not on a `v*` tag. A template pins features by digest, and a digest exists only once the feature is published. So a feature lands first, and a follow-up change pins it (`make pin-features`).

**The template pins them like any other feature.** `pin-features.sh` tracks both collections, and `neovim-go` references `…/trusted-devcontainer-templates/features/<id>@sha256:…`.

## Consequences

**Positive:**
- The template and its features change together, reviewed in one repository.
- Nothing in the editor is fetched unpinned. Plugins install at the commits in a committed `lazy-lock.json`, verified after install. CLIs are sha256-pinned per architecture, and Go tools are built at exact versions through the Go checksum database.
- The features are ordinary trusted features. Any template, here or elsewhere, can consume them.

**Negative:**
- Two feature collections to audit instead of one. ADR-006's "one repository" audit scope is amended accordingly.
- The feature pipeline is duplicated from the features repository and can drift from it. The ports say so at the top of each script.
- Release-Actor must accept deployments from `main` as well as `v*` tags (see `SETUP-ENVIRONMENTS.md`).
- `lazy-lock.json` is regenerated by `make lazy-lock`, the one deliberately unpinned operation. Its output is a reviewable diff of commit hashes.

## Alternatives Considered

| Alternative | Why not |
|---|---|
| **Build the features in trusted-devcontainer-features first** | The right home eventually; for a first version, every editor tweak would cost a cross-repository release cycle |
| **Local features inside the template (`src/neovim-go/.devcontainer/tmux/`)** | Ships with the template and needs no publishing, but cannot be digest-pinned, signed or reused by any other template |
| **Bake everything into the template's Containerfile** | Breaks ADR-002 (one shared Containerfile) and bypasses the feature contract's checksum and idempotency guarantees |

## Migration

When the features move to `trusted-devcontainer-features`:

1. Copy each `features/src/<id>` directory to `src/<id>` there. Revert `dependsOn` to `./bootstrap`; relative `installsAfter` references already match that repository's convention.
2. Release them there, then re-point `neovim-go` at `ghcr.io/infrashift/trusted-devcontainer-features/<id>` with `make pin-features`.
3. Delete `features/`, `release-features.yml` and `test-features.yml` here.
