# Dev user

All templates run as the dev user: the non-root user `dev`, with UID 1001 and GID 1001 (ADR-003).

## Where the user is set

| Item | Value | Set in |
|---|---|---|
| User and group | `dev`, `dev` | `shared/Containerfile`, `ARG USERNAME` |
| UID and GID | 1001, 1001 | `shared/Containerfile`, `ARG USER_UID`, `ARG USER_GID` |
| Shell | `/bin/bash` | `useradd -s` in `shared/Containerfile` |
| Home | `/home/dev`, with `~/.local/bin` on `PATH` | `ENV` in `shared/Containerfile` |
| Last `USER` | `dev` | `shared/Containerfile` |
| `containerUser` | `"dev"` | each `devcontainer.json` |
| `updateRemoteUserUID` | `false` | each `devcontainer.json` |
| `remoteUser` | not set | The devcontainer spec uses `containerUser` when `remoteUser` is not set. |

## How features find the user

A feature does not hardcode the user. It reads `_REMOTE_USER` and `_REMOTE_USER_HOME`, which the devcontainer CLI sets. If a variable is empty, the feature stops with an error. See [Bootstrap contract](/architecture/bootstrap-contract--01a18344b8d3.md).

The features repository also uses `dev` with UID 1001 (its ADR-011). The old `vscode` user with UID 1000 is superseded.

## Tests

`checkCommon` in `test/test-utils/test-utils.sh` runs in each template test. It checks that `whoami` is `dev`, that `id -u` is 1001, and that `id -g` is 1001. In the neovim templates, the `sshd` feature lets only the `dev` user log in.

## Analysis

* `CLAUDE.md` asks for `remoteUser` set to `dev`. No template sets `remoteUser`, but the effective value is `dev` because of `containerUser`.
* With `updateRemoteUserUID: false`, the UID in the container does not follow the UID on the host. A bind-mounted file can have a different owner.
* UID 1001 is not the usual first user UID (1000) on a Linux host. This prevents a conflict with that host user.
